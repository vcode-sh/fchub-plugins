Everything a developer needs to extend, integrate with, or debug FCHub Multi-Currency.

## REST API

All endpoints use the `fchub-mc/v1` namespace. Admin endpoints require `manage_options` capability and a valid `X-WP-Nonce` header.

### Public Endpoints

<Tabs items={['GET /context', 'POST /context', 'GET /rates']}>
<Tab value="GET /context">

Returns the current resolved currency context, including the price-formatting
metadata a client needs to fully re-render prices (not just the code and rate).

Reads `?currency=` from the query string with top priority in the resolver
chain — ahead of the cookie, and ahead of a signed-in visitor's saved account
preference. This makes the endpoint usable for client-side reconciliation:
`currency-projection.js` calls `GET /context?currency=<code>` to re-resolve a
saved localStorage preference on hosts that strip the guest cookie, without
depending on the cookie reaching the server at all.

**Response:**

```json
{
  "display_currency": "EUR",
  "display_currency_name": "Euro",
  "base_currency": "USD",
  "rate": "0.92140000",
  "source": "cookie",
  "is_base_display": false,
  "symbol": "€",
  "decimals": 2,
  "position": "right_space",
  "display_decimal_separator": ".",
  "display_thousand_separator": ",",
  "disclosure_enabled": true,
  "disclosure_text": "Prices shown in EUR are approximate. You will be charged in USD."
}
```

`source` is one of `url_param`, `user_meta`, `cookie`, `geo`, `default` — see
`ResolverSource`.

Every response — this endpoint and `POST /context`, every status — carries
`Cache-Control: no-store`. The response is resolved per visitor from their
cookie, account, and query string, so a cached copy would leak one visitor's
currency to another; a browser or intermediary that ignored this previously
silently served a stale response back to the reconciliation fetch described
below (issue #72). Client code calling this endpoint directly should also pass
`cache: "no-store"` (or equivalent) rather than relying on the header alone —
see the note in [Guest Currency Reconciliation](#guest-currency-reconciliation).

</Tab>
<Tab value="POST /context">

Sets the visitor's currency preference. Saves to cookie and user meta (if logged in). Fires `fchub_mc/context_switched`.

**Request body:**

```json
{
  "currency": "EUR"
}
```

**Response:** Same shape as `GET /context`, plus `code` (a stable outcome slug —
see below), `message`, `currency`, and `persisted`. Also carries
`Cache-Control: no-store` — see the note on `GET /context`.

A code that isn't 3 letters is rejected by the REST argument schema (400). A well-formed code not in the base/display currencies whitelist returns 422 (`invalid_currency`).

</Tab>
<Tab value="GET /rates">

Returns the latest exchange rates for all configured display currencies.

**Response:**

```json
{
  "base": "USD",
  "rates": {
    "EUR": "0.92140000",
    "GBP": "0.79230000",
    "PLN": "4.02150000"
  }
}
```

</Tab>
</Tabs>

## PHP API

### `fchub_mc_format_price(float $basePrice): string`

Converts a base-currency price to the visitor's display currency and returns formatted HTML.

```php
echo fchub_mc_format_price(99.99);
// Output: "€92.14" (when display currency is EUR with rate 0.9214)
```

Falls back to FluentCart's native formatter when the plugin is disabled or the visitor is in the base currency. Uses `bcmul` for precision when bcmath is available.

### JavaScript Globals

```javascript
// Switch currency programmatically (REST call + page reload)
window.fchubMcSwitchCurrency('EUR');

// Re-initialise all switcher widgets after dynamic content load
window.fchubMcInitSwitchers();

// Re-project prices on a specific DOM subtree
window.fchubMcProjectPrices(document.getElementById('my-container'));

// Update every switcher widget's visible "selected" state to a currency code,
// without a REST call or page reload. Used internally by currency-projection.js
// after client-side reconciliation (see below); rarely needed directly.
window.fchubMcSyncSwitcherDisplay('EUR');
```

### JavaScript Events

| Event | Target | Description |
|---|---|---|
| `fchub_mc:context_changed` | `window` | Fired before page reload after currency switch |
| `fchub_mc:context_switch_failed` | `window` | Fired when a currency switch is rejected server-side (module disabled, nothing to persist, invalid currency, rate limited). `detail: { currency, message, status, code }` |
| `fchub_mc:prices_projected` | `document` | Fired after each projection pass |
| `fchub_mc:context_reconciled` | `window` | Fired after `currency-projection.js` corrects a page served with a stale currency context — see [Guest Currency Reconciliation](#guest-currency-reconciliation) below. `detail: { currency, source }` |

- Unique ARIA IDs per instance for multiple widgets on one page

## Single Round-Trip Currency Switching

A currency switch already costs one round-trip before any of this: `POST
/context` to persist the choice, then a reload. Historically that reload was
a bare `window.location.reload()`, which left the freshly loaded page to
resolve its own currency however the resolver chain normally would — fine for
a signed-in visitor (`UserMetaResolver` resolves ahead of the cookie), but on
a host where a guest's cookie doesn't reliably reach the server on that same
reload (see [Guest Currency Reconciliation](#guest-currency-reconciliation)
below), the page would land on the wrong currency and need a second, separate
reconciliation fetch to correct itself — two slow round-trips stacked
sequentially where a signed-in visitor only ever pays one.

`currency-switcher.js`'s `switchCurrency()` already knows the exact currency
it just persisted, so instead of a bare reload it builds the reload URL with
that currency appended as the query parameter `UrlParamResolver` reads —
`UrlParamResolver` is Priority 1 in the resolver chain
(`ContextModule::buildResolverChain()`), ahead of the cookie and ahead of a
signed-in visitor's saved account preference, and reads `$_GET` directly on
any request, including this reload. That means the reload's own server-render
resolves the correct currency in this one request, for every visitor, without
depending on the cookie at all:

```javascript
// Simplified — see buildReloadUrl() and switchCurrency() in currency-switcher.js
const url = new URL(window.location.href);
url.searchParams.set(cfg.urlParamKey, currencyCode); // "currency" by default

// Not window.location.href = url.toString() — that navigates to a new URL,
// and any navigation to a new URL always opens a fresh history entry, which
// the browser always scrolls to the top regardless of where the visitor was
// on the page (confirmed live: this regressed scroll position on long pages).
// replaceState() rewrites the *current* entry's URL in place with no
// navigation, so the reload() that follows reloads that same entry instead
// of navigating to a new one — preserving scroll position exactly the way a
// plain reload() always did before this parameter existed. UrlParamResolver
// resolves the same query string either way; only the browser API used to
// get there differs.
window.history.replaceState(window.history.state, "", url.toString());
window.location.reload();
```

Because `RECONCILABLE_SOURCES` excludes `url_param` (see below), a page that
loads this way is never treated as a reconciliation candidate — the
`currency-projection.js` fallback correctly stays out of it entirely, with no
loading state and no second fetch.

If `urlParamEnabled` is `false` (the site owner disabled URL-parameter
resolution in settings), `buildReloadUrl()` returns `null` and
`switchCurrency()` falls back to a plain `window.location.reload()`, exactly
as before — it never assumes a resolver that isn't in the chain.

Once the reloaded page has settled, `currency-projection.js` removes the
currency parameter from the visible URL again via `history.replaceState()` —
no navigation, no visible change — so the address bar doesn't accumulate
`?currency=EUR` after every switch, and a CDN in front of the page doesn't
get a reason to cache each currency as a separate URL. This only ever touches
the URL when `source` is `url_param` on the current page; it never rewrites
the address bar for a cookie/geo/default/user_meta resolution.

## Guest Currency Reconciliation

Some hosts run an edge/WAF layer that strips cookies by default on any URL path
that hasn't been explicitly whitelisted, scoped per-path rather than sitewide.
On such hosts, a logged-out visitor's `fchub_mc_currency` cookie never reaches
WordPress on an ordinary page load, so the resolver chain falls through past
`CookieResolver` to geolocation or the store default — even though the browser
still has the cookie and the visitor never changed their mind. Signed-in
visitors are unaffected: their preference lives in user meta, a second,
independent channel `UserMetaResolver` resolves ahead of the cookie.

This is a different scenario from [Single Round-Trip Currency
Switching](#single-round-trip-currency-switching) above: that section covers
the reload immediately after a switch, which now resolves correctly in one
request via the URL parameter and never reaches this fallback at all
(`source` is `url_param` there, and `RECONCILABLE_SOURCES` excludes it). This
section covers a guest arriving at *any other* page load — a fresh visit, a
bookmark, a full-page cache hit — where the cookie set by an earlier switch
doesn't reach the server.

The plugin adds a client-side fallback that doesn't depend on the
cookie round-tripping through that layer:

1. `currency-switcher.js` mirrors a guest's choice into `localStorage`
   (`fchub_mc_currency`) in addition to the existing cookie/REST persistence,
   gated on `guestLocalStorageEnabled` (mirrors the `cookie_enabled` setting —
   a site that disabled guest persistence outright doesn't get it back through
   a side door).
2. `currency-projection.js` compares that localStorage value against the page's
   baked-in `displayCurrency` on load. It only acts when the page's `source` is
   `cookie`, `geo`, or `default` — never `url_param` or `user_meta`, so an
   explicit link or a signed-in visitor's saved preference is never
   second-guessed by a stale local value. The same symptom this also covers a
   full-page/edge cache (Cloudflare, Rocket.net's own edge tier, etc.) serving
   a shared, anonymous-visitor snapshot of the page — the visitor's cookie
   never gets stripped in that case, it's simply irrelevant to what HTML the
   cache returns, since the request never reaches WordPress/PHP at all.
3. If they disagree, the switcher's trigger is immediately synced to the
   localStorage value — the visitor's own choice, not the page's stale
   baked-in one — and dimmed/non-interactive (`fchub-mc-switcher--loading`)
   for the duration. Prices, by contrast, are left completely untouched — no
   hiding, no dimming, no projection pass at all — until reconciliation
   actually completes, at which point they go directly from whatever the
   page originally rendered to the corrected, converted values in one step.
   Only the trigger shows a loading state during the wait; prices get none.
   The fetch itself is `GET {restUrl}/context?currency=<code>` — which
   resolves via the URL query string, not the cookie — and on response,
   reassigns the mutable projection state in place, clears and runs price
   projection for the first time, and calls
   `window.fchubMcSyncSwitcherDisplay()` again to reflect whatever the server
   actually confirmed (normally the same value already shown; if the server
   disagrees with the visitor's saved choice — rare — this corrects the
   trigger to match the server instead). `fchub_mc:context_reconciled` fires
   on `window` afterwards.
4. The localStorage value is validated against the base currency and enabled
   display currencies baked into the page (mirroring
   `AllowedCurrencyCheck::isAllowedCurrency()`) before it's ever trusted, and
   the server independently re-validates it again via the normal resolver
   chain — a stale or tampered localStorage value can't force an unsupported
   currency.

### The reconciliation fetch must never be cache-servable

Step 3's `fetch()` call passes `cache: "no-store"`, and the endpoint responds
with `Cache-Control: no-store` (see `GET /context` above) — both are load-bearing,
not defensive nicety. Confirmed live on issue #72: with the header alone but no
`cache: "no-store"` on the request, once a given `?currency=X` URL had been
fetched once in a browser profile, the browser served that same response from
its own HTTP cache on every later reconciliation attempt — status 200, no real
round trip — even though the endpoint itself was resolving correctly and a
fresh direct navigation to the same URL always returned the right answer. The
page kept silently settling back on the stale currency. If you build your own
client against this endpoint for the same purpose, set `cache: "no-store"` (or
your HTTP client's equivalent) rather than relying on the response header
alone — a response already cached from before the header shipped would still
be reused without it.

### The reconciliation timeout is sized for real host latency, not the happy path

`reconcile()` bounds its fetch with an `AbortController` — `RECONCILE_TIMEOUT_MS`,
currently 12s — past which it gives up and leaves the page on whatever currency
it was served with, rather than hanging indefinitely. This isn't a nicety
figure. Confirmed live on a Rocket.net staging tier: `GET /context` can take
several seconds under ordinary page-load conditions, because it competes with
the rest of the page's own PHP-driven requests (other plugins' AJAX calls
included) for the same PHP-FPM worker pool — a concurrent, unrelated
`admin-ajax.php` call on the same page load alone took 5.4s. A timeout sized off
an isolated, uncontended measurement of this endpoint (which responds in a few
hundred ms on its own) will intermittently abort before a legitimate response
arrives on a busy or resource-constrained host, silently defeating
reconciliation with no error surfaced anywhere.

The CSS safety-net fallback (`fchub-mc-fouc-fallback` in
`currency-switcher.css`, force-revealing prices if `.fchub-mc-projecting` is
never removed at all) is set well behind this bound — 15s — specifically so it
never fires while a legitimate reconciliation is still in flight. It exists
only to guarantee the page doesn't hide content forever if JavaScript itself is
broken, not to race `RECONCILE_TIMEOUT_MS` on a shorter clock. If you tune
`RECONCILE_TIMEOUT_MS` for your own hosting environment, keep the CSS value
ahead of it with real margin.

## GDPR / Privacy

The plugin registers with WordPress's privacy tools:

### Personal Data Exporter

Exports for a given email address:
- User meta `_fchub_mc_currency` (preferred currency preference)
- All `fchub_mc_event_log` rows for the user (event name, timestamp; paginated at 50 per page)

### Personal Data Eraser

Deletes for a given email address:
- `_fchub_mc_currency` user meta
- All `fchub_mc_event_log` rows for the user
