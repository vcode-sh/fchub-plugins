### v1.1.0

*Released 9 August 2026* — [GitHub Release](https://github.com/vcode-sh/fchub-plugins/releases/tag/fchub-portal-extender/v1.1.0)

Endpoints can now choose where they sit in the customer portal menu, instead of
always queuing up behind Profile like everybody else.

#### Menu Placement

Requested by @Joe-Bloggs in [#62](https://github.com/vcode-sh/fchub-plugins/issues/62) and tracked in [#141](https://github.com/vcode-sh/fchub-plugins/issues/141). The endpoint editor has a new
**Menu Placement** field: put an endpoint at the top, directly under Dashboard,
after any other built-in item, or at the very bottom. Existing endpoints keep
the slot they already had, so upgrading moves nothing.

FluentCart's API drops every custom endpoint immediately before `profile` and
offers no position argument, so the finished menu is reordered afterwards on
`fluent_cart/global_customer_menu_items`. Items belonging to other plugins are
passed through untouched — this reorders, it never curates.

#### Placement is anchored, not numbered, and that is the interesting part

FluentCart's menu is not the same for every visitor: it hides **Licenses**
without Pro or with the license module off, and hides **Subscription Plans**
from customers who have none. An absolute "position 2" would therefore land
beside a different neighbour for different people — a promise nobody can keep.

So placement anchors to a named item and degrades honestly. Choose "After
Licenses" on a site with no licenses and the endpoint takes the slot where
Licenses would have been, by walking up to the nearest visible item. "Before
Subscription Plans" walks down for the same reason. Either way it lands in the
same visual gap rather than at the bottom of the menu.

#### Portal Extender has tests now

It had none. It has 57, covering placement resolution, hidden anchors, grouped
endpoints, third-party items surviving a reorder, and the icon sanitiser
whitelist from 1.0.4 — including a test that scans every permitted attribute for
anything shaped like an event handler, so that whitelist cannot quietly widen
later. The plugin is now in the CI matrix on PHP 8.4 and 8.5.

### v1.0.4

*Released 9 August 2026* — [GitHub Release](https://github.com/vcode-sh/fchub-plugins/releases/tag/fchub-portal-extender/v1.0.4)

Endpoint icons now appear on the front end, which is where icons are generally
most useful.

#### Icons survive the trip to the customer portal

Reported by @Joe-Bloggs in [#62](https://github.com/vcode-sh/fchub-plugins/issues/62): the icon showed in the admin, picked correctly,
saved correctly — and then rendered as nothing at all in the portal.

FluentCart runs every portal menu icon through `wp_kses()` with a whitelist of
`svg`, `path` and `g`. Nothing else survives. A Dashicon is a `<span>`, so it was
deleted outright and could never render. Any SVG built from `circle`, `rect`,
`line` or `polyline` came out as an empty `<svg></svg>`. And `viewBox` was
stripped from everything, because `wp_kses` lowercases attribute names before
matching while the whitelist key is camelCase.

Portal Extender now widens that whitelist through FluentCart's own
`fct_allowed_svg_tags` filter, merging on top of it rather than replacing it, so
other plugins' entries survive. The shape elements, the stroke and fill
presentation attributes, lowercase `viewbox` and the Dashicon `<span>` are all
allowed through.

It remains a whitelist. `script`, `foreignObject`, `use`, `xlink:href`, `href`,
inline event handlers and `style` on SVG elements are still stripped, and that
is covered by a test that throws a deliberately hostile icon at it.

#### Dashicons are actually loaded now

Surviving sanitisation is only half of it — WordPress does not load the
Dashicons stylesheet on the front end for ordinary visitors, so the markup would
have rendered as an empty box regardless. The stylesheet is now enqueued on the
portal, and only when an active endpoint genuinely uses a Dashicon.
