Start with **Memberships > Dashboard**. Version 1.4.0 brings setup readiness,
failed notifications, provider health, and recent activity into the workspace
so many problems can be found without beginning in the database. Progress.

## A purchase did not grant access

<Steps>
<Step>

**Confirm the payment**

Open the FluentCart order and make sure payment completed. Pending, failed, and
abandoned orders do not grant membership access.

</Step>
<Step>

**Check the product connection**

Open **Memberships > Plans**, edit the expected plan, and check **Linked
Products**. For an advanced FluentCart feed, confirm that the feed is enabled
and points to the right plan.

</Step>
<Step>

**Find the customer**

Open **Memberships > Members** and search by the order email. If the order was
placed as a guest, confirm that the connection is allowed to create or match a
WordPress user.

</Step>
<Step>

**Review recent activity**

The dashboard and member profile show whether access was granted, skipped, or
later changed. The FluentCart order log provides the matching purchase-side
message.

</Step>
</Steps>

## A member cannot open protected content

<Accordions type="single">
<Accordion title="The member has no active plan">

Open the member profile and check whether access is active, paused, expired, or
revoked. Also check future start dates and upcoming or passed expiry dates.

</Accordion>
<Accordion title="The content is still waiting to unlock">

Open the plan's drip timeline. A member may own the content while its delay or
fixed unlock date is still in the future.

</Accordion>
<Accordion title="The content belongs to another plan">

Open **Memberships > Content** and inspect the protection rule, then compare it
with the member's active plans. Plan relationships can include lower tiers, but
an unrelated plan does not.

</Accordion>
<Accordion title="A cache keeps showing the wrong version">

Exclude protected pages from public full-page caching, or use a cache that
varies by signed-in member. Purge the affected page after changing protection
or access.

</Accordion>
</Accordions>

## Protected content is public

1. Open **Memberships > Content** and confirm the rule exists.
2. Make sure at least one selected plan is active.
3. Test while logged out or as a non-administrator; administrators bypass
   protection by default.
4. Check the feed, archive, search, and REST view as well as the main page.
5. Purge page and object caches after changing the rule.

If only one public channel leaks full content, record the exact URL and request
type before changing the rule. “WordPress did something” is emotionally valid
but not yet a reproduction.

## Email issues

<Accordions type="single">
<Accordion title="No built-in email was sent">

Open **Memberships > Settings > Email Studio** and confirm the message uses
**Built-in email** rather than **FluentCRM automation** or **Off**. Send a test,
then inspect **Tools > Scheduled Actions** for a failed Memberships email.

Finally, verify normal WordPress email delivery and sender-domain
authentication with your mail provider.

</Accordion>
<Accordion title="The message looks wrong">

Preview the message in Email Studio, check its individual style override, and
compare it with the shared brand template. Send a fresh test after saving.

</Accordion>
<Accordion title="A FluentCRM automation did not start">

Confirm FluentCRM is active, the automation is published, the member has a
matching FluentCRM contact, and that the notification is assigned to
**FluentCRM automation** where applicable.

Open **Memberships > Integrations** for pending, failed, or drifted CRM work.

</Accordion>
</Accordions>

## Provider access is out of sync

Open **Memberships > Integrations** before manually changing the provider.

1. Check whether the provider and required capability are available.
2. Review pending and failed operations.
3. Preview reconciliation to see what Memberships believes should change.
4. Repair one member first.
5. Use the bounded all-member repair only after the preview is sensible.

Optional provider features stay hidden or unavailable when their runtime
contract is not supported. Installing a plugin and activating a supported
capability are not the same achievement.

## Webhook problems

<Accordions type="single">
<Accordion title="An endpoint cannot be activated">

The endpoint needs its own secret and a successful one-shot test. Confirm that
the destination is public HTTPS, generate or rotate the secret, update the
receiver, and run the test again.

</Accordion>
<Accordion title="Deliveries keep retrying">

Open delivery history and inspect the latest response. Fix the receiver first;
automatic retries use increasing delays. A terminal failure can be retried
manually after the destination is healthy.

</Accordion>
<Accordion title="A delivery should not run anymore">

Cancel it while it is pending or retrying. Pause the endpoint if no new events
should be created for that destination.

</Accordion>
<Accordion title="The receiver processed an event twice">

Webhook delivery is at least once. The receiver must remember the stable event
ID before applying the effect and treat a repeated ID as the same event.

</Accordion>
</Accordions>

## API connection problems

<Accordions type="single">
<Accordion title="The read-only access check is unauthorised">

Generate a current access key and send it in the `X-API-Key` header. Query-string
keys are rejected. The built-in connection guide contains the exact endpoint
for this site.

</Accordion>
<Accordion title="A membership change is rejected">

External writes require HTTPS, a WordPress Application Password, a user with
the membership-management capability, and a unique `Idempotency-Key` header.
The read-only FCHub key cannot manage members.

</Accordion>
<Accordion title="Reusing an idempotency key returns a conflict">

The same key may repeat the same operation and payload. A different operation
or payload needs a new key.

</Accordion>
</Accordions>

## Still stuck?

Collect the affected member, plan, content or endpoint, the time of the latest
attempt, and the visible workspace error. Then use the
[Developer Reference](/docs/fchub-memberships/developer-reference) for exact
routes, hooks, commands, and payload contracts.
