The stdio transport is the local transport recipe for clients such as Claude Desktop and Cursor. For remote agents or a public endpoint, run the HTTP transport on a server somewhere.

## Docker Image

The image is on Docker Hub and GitHub Container Registry, built for `linux/amd64`. That covers every ordinary VPS. On an arm64 host it runs under emulation, or you build it yourself from the tab below — which takes about a minute and skips the emulation tax.

<Tabs items={['Docker Hub', 'GitHub Container Registry', 'Build from source']}>

The container exposes port `3000` and starts with `--transport http` by default. Your MCP endpoint lives at `http://localhost:3000/mcp`.

## Environment Variables

| Variable | Required | Description |
|---|---|---|
| `FLUENTCART_URL` | Yes | Full URL to your WordPress site |
| `FLUENTCART_USERNAME` | Yes | WordPress username the server authenticates as |
| `FLUENTCART_APP_PASSWORD` | Yes | WordPress Application Password |
| `FLUENTCART_MCP_API_KEY` | Yes, for any bind that isn't loopback | Bearer token for `/mcp`. At least 32 characters. |
| `FLUENTCART_MCP_ALLOWED_HOSTS` | Yes, in the private profile | Comma-separated hostname allowlist. |
| `FLUENTCART_MCP_ALLOWED_ORIGINS` | Yes, in the private profile | Comma-separated browser Origin hostname allowlist. |
| `FLUENTCART_WRITE_MODE` | No | `disabled` (default) or `reversible` |
| `FLUENTCART_TIMEOUT` | No | Request timeout in milliseconds. Default 30000 |

## Binding and Authentication

The HTTP transport binds `127.0.0.1` by default. The Docker image overrides that with `--host 0.0.0.0`, because a container that only talks to itself is a philosophical exercise rather than a deployment.

The **local profile** is the loopback default. The Docker entry point selects the **private
profile** because it binds `0.0.0.0`. Private HTTP requires
`FLUENTCART_MCP_API_KEY` of at least 32 characters and both allowlists above; every check runs
*before* the server listens. Miss one and you get an exit, not an exciting new unauthenticated
store endpoint.

Once a key is set, every request to `/mcp` needs `Authorization: Bearer <key>`. Every rejection — no header, malformed header, wrong key — returns the same thing:

```json
{"error":"Unauthorized"}
```

Identical body, identical status, and the comparison is constant-time. A prober cannot tell a wrong key from a missing one, or measure its way towards a right one.

<Callout type="warn" title="The key protects the endpoint, not your store">
A bearer key stops strangers reaching your MCP endpoint. It does not decide what that endpoint can do — `FLUENTCART_WRITE_MODE` does, and it defaults to `disabled`. Leave it there unless you have a reason not to. The most secure deployment is still one where nothing dangerous is exposed in the first place.
</Callout>

The bearer token is one static transport principal mapped to one configured WordPress principal.
2.0.0 has no OAuth and no multi-user identity mapping. If two callers need different store roles,
run two separately configured processes; one token does not magically become an identity provider
because it crossed a reverse proxy.

## Refunds and Cancellations in 2.0.0

They are not part of this server. `fluentcart_order_refund` and
`fluentcart_subscription_cancel` are absent, and no environment variable enables them. Use
FluentCart's admin or its official operator tooling for those jobs.

## Safe Release Recovery

The staging workflow records the inspected package as npm `next` together with versioned Docker
images. A separate owner-triggered promotion rechecks the immutable evidence before moving those
same bytes to npm `latest`, updating matching Docker tags, and creating the GitHub Release.

Published package versions are immutable: never reuse a version. If a candidate is unsuitable,
deprecate it, restore mutable tags to the previously recorded digests where necessary, fix the
source, and publish a new patch version. Recovery consumes recorded artefact identities; it does
not rebuild an old version and hope for the same bytes.

## Dokploy Setup

If you're running [Dokploy](https://dokploy.com) (or similar), point it at the image and you're done in about 90 seconds.

<Steps>
<Step>

**Create a new application** — choose **Docker Image** as the source and set the image to `vcodesh/fluentcart-mcp:latest`. Or if you prefer building from Git: point it at the repo with build context `fluentcart-mcp/`.

</Step>
<Step>

**Set environment variables** — the three FluentCart credentials plus
`FLUENTCART_MCP_API_KEY`, `FLUENTCART_MCP_ALLOWED_HOSTS`, and
`FLUENTCART_MCP_ALLOWED_ORIGINS`. Set both allowlists to the hostname exposed by Dokploy, your
reverse proxy, or your tunnel. The container binds beyond loopback, so an incomplete private
profile exits instead of starting.

</Step>
<Step>

**Deploy** — exposed port is `3000`. The container starts the HTTP transport automatically.

</Step>
</Steps>

## Cloudflare Tunnel

If you're using Cloudflare Tunnels (and you should be — free SSL, no port forwarding, no firewall fiddling):

1. In Cloudflare Zero Trust dashboard, add a public hostname
2. Set the subdomain (e.g. `mcp.your-domain.com`)
3. Point it at `http://localhost:3000` (or whatever your container's internal address is)
4. Save

Your MCP endpoint is now at `https://mcp.your-domain.com/mcp`. Encrypted, routed through
Cloudflare's network, and still protected by the MCP bearer key.

## Health Check

```bash
curl https://mcp.your-domain.com/health
```

Should return:

```json
{"status":"ok"}
```

`/health` is deliberately unauthenticated so load balancers and uptime monitors can reach it. It says nothing about your store — only that the process is alive. The bearer key guards `/mcp` and nothing else needs it.

If it doesn't answer, something's broken. Check the container logs:

```bash
docker logs fluentcart-mcp
```

## Connecting Clients

### ChatGPT

If your ChatGPT account offers custom MCP connector configuration, add your endpoint URL there:

```
https://mcp.your-domain.com/mcp
```

ChatGPT is deployment guidance, not a certified client. Check its current connector requirements, then add the bearer token in the applicable auth settings. A non-loopback FluentCart MCP endpoint will not start without its bearer key.

### Any HTTP-capable MCP client

Point a client that supports Streamable HTTP at your `/mcp` endpoint and set the bearer token when configured. Check the client’s own MCP documentation for its transport and authentication requirements.

<Callout type="info" title="Stateless mode">
The HTTP transport creates a fresh server instance per request. That keeps things simple and works
with scale-to-zero deployments, at the cost of resolving config and rebuilding the registry each
time. Dynamic mode keeps that surface to three read tools, or four when reversible writes are
enabled.
</Callout>

## Docker Compose

If you prefer compose (or want to run it alongside other services):

```yaml title="docker-compose.yml"
services:
  fluentcart-mcp:
    image: vcodesh/fluentcart-mcp:latest
    ports:
      - "3000:3000"
    environment:
      FLUENTCART_URL: https://your-store.com
      FLUENTCART_USERNAME: admin
      FLUENTCART_APP_PASSWORD: "aBcD eFgH iJkL mNoP"
      FLUENTCART_MCP_API_KEY: "a-32-character-minimum-secret-goes-here"
      FLUENTCART_MCP_ALLOWED_HOSTS: mcp.your-domain.com
      FLUENTCART_MCP_ALLOWED_ORIGINS: mcp.your-domain.com
    restart: unless-stopped
```

```bash
docker compose up -d
```

The compose service is configured to survive reboots until you stop it.

Need the old CLI while upgrading? Pin the explicit fallback:

```bash
npx -y fluentcart-mcp@1
```
