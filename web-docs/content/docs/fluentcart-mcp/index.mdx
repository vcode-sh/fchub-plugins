FluentCart's admin panel is fine if you enjoy clicking through seventeen screens to find out what last week actually earned. For everyone else, there's this — an MCP server that connects your AI assistant to your store's REST API. Claude, Cursor, Copilot, ChatGPT, Codex, anything that speaks MCP.

Out of the box it reads. Orders, products, customers, subscriptions, reports, settings. Changing anything is a separate decision you have to make on purpose, and the tools that touch money are hidden until you have configured the machinery that makes them safe to expose.

Open source. On [npm](https://www.npmjs.com/package/fluentcart-mcp). On [GitHub](https://github.com/vcode-sh/fchub-plugins).

<Callout type="info" title="No AI Expertise Required">
You don't need to understand how MCP works. If you can double-click a file or paste a config snippet, you're overqualified.
</Callout>

## Quick Start

**Claude Desktop — one click:**

Download <McpbDownload />, double-click, enter your WordPress credentials. Done. No Node.js, no JSON, no terminal.

**Everyone else:**

```bash
npx fluentcart-mcp setup
```

Asks three questions (WordPress URL, username, Application Password), tests the connection, saves the config. Then point your AI client at `npx fluentcart-mcp`. The [Setup Guide](/docs/fluentcart-mcp/setup) covers every platform step by step.

## What You Can Do

You just talk. The AI finds the right tool and fills in the parameters:

> "Show me all orders from the last 7 days"

> "Find the customer with email john@example.com and show their order history"

> "What's my revenue this month compared to last month?"

> "Which products sold best in the last quarter, and how does that compare to the one before?"

> "Show me every subscription that renews in the next fortnight"

Those work on a default install. Anything that changes data — a new product, a price update, a shipping zone — needs `FLUENTCART_WRITE_MODE` set first, and the server will not pretend otherwise: a tool it hasn't exposed cannot be listed, searched, described or called by name.

## Read-Only Until You Say Otherwise

`FLUENTCART_WRITE_MODE` decides what the server is even willing to show your AI. It defaults to `disabled`.

| Write mode | What appears | Use it when |
|---|---|---|
| `disabled` *(default)* | Reads only | You want answers, not edits |
| `reversible` | Reads plus the writes that can be undone — creating and updating products, variants, coupons, customers, shipping, tax rules, attributes and order bumps | You want the AI to do the boring admin |
| `guarded` | The same set as `reversible` in 2.0.0 — see below | Nothing yet. It's the mode the money tools will return to |

Filtering happens before registration, not at call time. A tool the policy excludes is not disabled — it is absent, and cannot be listed, searched, described or called by name.

<Callout type="warn" title="Refunds and cancellations are not available in 2.0.0">
`fluentcart_order_refund` and `fluentcart_subscription_cancel` are **not available in any write mode**, including a fully configured `guarded` one. If you are here to automate refunds, this release will not do it and you should know that before you install rather than after.

The guard itself is finished — signed previews pinned to the exact payload, a durable single-writer ledger, replay and conflict detection, crash handling that never silently retries. What is missing is acceptance evidence, and for something that moves customer money that distinction is the whole argument. Proving a refund end to end needs an order created, refunded and then removed within one run, and FluentCart 1.5.5 offers no way to finish that: transactions have no DELETE route, deleting an order leaves them behind, and no draft product can stand in because unpublished products can't be purchased. Every candidate fixture leaves residue the API cannot clean up.

The rule we set ourselves was that a guarded capability either passes both acceptance lanes or ships unavailable. It could not, so it does not. The ceremony is built; the proof is not, so it is not switched on.
</Callout>

Deletion, bulk operations, order status changes and marking an order paid are also absent, for the same reason in a milder form: FluentCart offers no supported way to undo them, so they are not classed as reversible.

## How It Works

1. **You ask** your AI something — "Show me today's orders"
2. **The AI picks** the right tool and calls the MCP server
3. **The MCP server** makes an authenticated call to your WordPress site
4. **FluentCart** does the work and returns the data
5. **The AI** tells you what happened, in plain English

No API calls. No JSON. Just a conversation.

<Callout type="warn" title="Your Store, Your Data">
The MCP server connects directly to **your** WordPress site. Nothing passes through third-party servers. Your data stays between your AI client and your WordPress installation.
</Callout>

## What You Need

| Requirement | Details |
|-------------|---------|
| **WordPress** | 7.0.2 with [FluentCart](https://fluentcart.com) 1.5.5 and FluentCart Pro 1.5.4 — the combination this release is verified against |
| **Application Password** | Generated in WordPress admin (Users → Profile) |
| **Node.js 24+** | [Download](https://nodejs.org) — *not needed for the Claude Desktop Extension* |

Older FluentCart builds are a different question. The route surface of an older 1.3.9 install has been captured from a real runtime, so there is hard evidence of which endpoints that build serves — but evidence about a store is not the same as proof these tools work against it, and support for it isn't claimed.

What does happen on any store, old or new: the server reads your REST index at startup and registers only the tools your routes can serve. An older build gets a smaller tool list rather than a full one that fails halfway through.
